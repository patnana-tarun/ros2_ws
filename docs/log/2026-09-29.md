# 2026-09-29

## Done
- **Sender ([[mesh_nodes]]), formatting:** import order, a mis-indented comment and docstrings;
  `ament_flake8`, `ament_pep257` and `ament_xmllint` are clean. Added the missing
  `ament_index_python` dependency (the launch file uses it).
- **Sender, fixes:**
  - `transmission_stamp` is now wall time even under `use_sim_time` ([[Message envelope]]).
  - The throttle hold and status heartbeats run on the wall clock ([[Map-in-flight throttle]]).
    Before, with sim time and no `/clock`, the throttle never switched off.
  - One reusable hold timer instead of a new timer per map; a hold of 0 disables the throttle.
  - Clean exit on Ctrl+C (`rclpy.try_shutdown`).
- **Receiver ([[Receiver (external)]]):** turned the loose scripts in `~/ros2_ws/mesh_nodes` on
  the Pi into an ament_python package with a launch file and YAML, and fixed:
  - `raw_mesh_event_logger` subscribed to `/mesh/tf` as RELIABLE against the BEST_EFFORT
    publisher ([[QoS design]]), so it had never recorded a TF row.
  - `tf_rolling_metrics` pruned its window by the sender's clock but measured it with its own.
    With the clocks apart, `packet_count` and throughput grew without bound and PDR stuck at
    100 %. It now prunes by receive time, the clock its expected count already uses.
  - `batctl` calls (up to 3 s) blocked the only executor thread, so TF could overflow the queue
    exactly when the link was bad. They now run in their own callback group on a
    multi-threaded executor.
  - Ctrl+C crashed in `rclpy.shutdown()` and was logged as FATAL; the logger's dedup set grew
    forever. Both fixed.

## Verified
- Sender, in one process with `use_sim_time:=true` and no `/clock`: 10/10 TF forwarded, 4/10
  during the map hold (2 of 5), then full rate again; the map stamp was wall time.
- Sender and receiver together, in one process on the laptop: 150 TF in, 123 forwarded (20 flagged
  `map_in_flight`), `tf_rolling_metrics` 123/123 = 100 % PDR, and the raw logger recorded the same
  123 TF rows. All three nodes exit cleanly on Ctrl+C.

- **Over the real mesh**, relay on the laptop and receiver deployed on the Pi, fake `/tf` at
  20 Hz for 32 s with two 40 kB maps:
  - TF seq 58–589 arrived with no gaps, no duplicates and one session. The first 57 were sent
    before discovery finished.
  - PDR 99.5–100 %, latency avg ≈ 16 ms (min 2.9, max 114), jitter ≈ 8 ms, 1 hop, TQ 238–243.
  - Map latency 73 ms and 53 ms. 32 TF samples were flagged `map_in_flight`, the expected
    2 of 5 × 2 s × 20 Hz × 2 maps.
  - The raw logger recorded all of it. No tracebacks, and both receiver nodes closed cleanly.

## Found
- The Pi's clock read 2026-06-05 and was unsynchronised at the start of the session. It had
  synced by the mesh test ([[Known limitations]] #21).
- Both machines use discovery-server mode ([[Discovery server not running]]). A relay started in
  the background of a non-interactive shell ignores SIGINT and needs SIGTERM (test harness only).
- With zero TF missing, PDR still dipped to 99.5 % at the end of the run. That comes from the
  heartbeat timing at the window edge (about 1 packet in 360), not from loss ([[PDR measurement]]).
- Two senders on one domain put `tf_rolling_metrics` into a reset loop (#22). Seen when a stray
  test relay was still running.

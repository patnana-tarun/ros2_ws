# 2026-10-14

## Done
- Receiver Pi time sync ([[Known limitations]] #21): `chrony.service` was disabled on the Pi, so
  chronyd never started at boot and the clock stayed at 2026-06-05. Ran
  `sudo systemctl enable --now chrony` on the Pi. Its `chrony.conf` was already correct
  (`server 192.168.123.1 iburst minpoll 2 maxpoll 4`, `makestep 1 3`).
- After a reboot the Pi was back at 2026-06-05 and didn't sync until chrony was restarted
  several times. Second cause found: `~/demo_com/start-mesh.sh` sets `wlan0` unmanaged, which makes
  NetworkManager run `20-chrony-onoffline` while `bat0` has no address, so chrony marks
  192.168.123.1 offline (journal: `Source 192.168.123.1 offline` at 143 s). NM never manages `bat0`,
  so the source stays offline. Added step 8 to `start-mesh.sh` (backup:
  `start-mesh.sh.bak-2026-10-14`): wait for the laptop to answer ping, then `chronyc online`,
  `burst 4/4`, `makestep`, `waitsync`, and print the result. Updated [[Known limitations]] #21.
- Wrote `~/demo_com/pi-zero-2w/start-mesh.sh` and `stop-mesh.sh` for a Pi Zero 2 W on
  Raspberry Pi OS Lite 64-bit. Added [[Mesh network setup]], which holds the mesh settings, node
  addresses and what the Zero scripts do. Linked it from Home.
- SSH to the Pi Zero 2 W (192.168.123.3) failed with "REMOTE HOST IDENTIFICATION HAS CHANGED":
  `~/.ssh/known_hosts` still held the key of the earlier device at .3. The host now reports
  `OpenSSH_10.0p2 Debian-7+deb13u4` (Raspberry Pi OS, Trixie), so the new key was expected. Removed the old
  entry (`ssh-keygen -R`, backup in `known_hosts.old`) and accepted the new key.
- Adapted the Zero scripts to the real Zero (Trixie, NetworkManager, timesyncd) and deployed them
  to `~/demo/` on the Zero. The user's originals are kept as `*.bak-2026-10-14`. The changes:
  - scan for the live cell BSSID (the user's original hardcoded `F2:60:C5:80:E9:FF`)
  - fixed `bat0` MAC plus a gratuitous ARP
  - detach on `bat0` SSH as well as `wlan0`
  - 120 s laptop wait with TQ progress
  - a timesyncd check that waits for a reply from the laptop
  - dropped the MTU 1560 attempt (`wlan0` maxmtu is 1500)
  - Bullseye/dhcpcd code removed
  Details: [[Mesh network setup]].

## Verified

- Pi: `^* 192.168.123.1`, stratum 7, clock stepped −3136 h to 2026-10-14 within a few seconds of starting.
- `chrony` is now `enabled` (symlink in `multi-user.target.wants`).
- After the reboot, chrony started at boot, then synced 13 s after the last manual restart (stepped +11 291 695 s).
- Step 8 on its own: with the source forced offline (`chronyc offline`, shown as `^?`), it brought it
  back to `^* 192.168.123.1` and printed "Clock synced" in 10 s.

- Both Zero scripts pass `bash -n`. The IBSS-mode detection was tested against `iw` output: a sample,
  and the laptop's phy0. An earlier regex missed the space before `*` and would have rejected every chip.

- On the Zero, timesyncd with the drop-in synced from the laptop's chrony 1 s after a restart
  (offset +418 ms).
- `start-mesh.sh` run live on the Zero four times over SSH on `bat0` (it detached itself), with a
  safety net that would fall back to the original script; the safety net never fired. Final run:
  found cell `f2:60:c5:80:e9:ff` by scan, laptop reachable after 27 s, "Clock synced to laptop",

  to the laptop appears at once, but TQ climbs from about 100 to 153 before ping works (32 s that

- The scan parser was tested on a sample with an AP, two IBSS cells and another SSID: it picks the
  strongest `robot-mesh` IBSS cell.

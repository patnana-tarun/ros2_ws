# Known limitations

| # | Area | Issue | Possible fix |
|---|------|-------|--------------|
| 1 | Relay | `/tf_static` is not relayed, so the receiver never gets `base_link → laser_frame` and the other fixed frames | receiver runs its own robot_state_publisher, or relay `/tf_static` |
| 2 | Relay | All of `/tf` is forwarded. In simulation that includes 6 wheel and 2 bogie transforms, which means heavy mesh traffic | filter by frame (e.g. keep `map→odom`, `odom→base_footprint`) |
| 5 | Relay | Parameters are read only at startup | add a parameter callback |
| 6 | Interfaces | `MeshScan` wraps `OccupancyGrid` and its field order differs from `MeshMap` ([[my_mesh_interfaces]]) | fix it before first use |
| 7 | Sim | Yaw from the EKF drifts slowly: gyro only, no magnetometer ([[Odometry fusion]]) | SLAM corrects it through `map → odom` |
| 8 | Model | All masses and the LiDAR/Pi sizes are assumed ([[Robot model]]) | weigh and measure the parts |
| 9 | Sim | The X2 model uses datasheet figures. Real X2 noise and dropouts on dark, wet rock are unknown | compare with a real scan |
| 10 | Sim | In the [[Cave world]] the LiDAR sees the visual wall a few cm behind the collision wall | lower `COLLISION_Z` if it matters |
| 11 | Sim | Cave lamps cast no shadows, so light leaks through rock into neighbouring passages | shadowed lights (slower) |
| 12 | Sim | The cave layout is fixed. `--seed` only changes rock detail, not the chambers or tunnels ([[Cave world]]) | randomise `CHAMBERS`/`TUNNELS` for training variety |
| 13 | Sim | The closed cave is dark, and the robot has no camera or headlight | add them if vision is needed |
| 14 | Navigation | The 2D LiDAR only sees what crosses its scan plane at 0.18 m. Rocks lower than that are invisible to it, and the robot can only climb about 5–6 cm ([[Rock climbing]]). Rocks between about 6 and 18 cm can therefore stop it unseen; in an earlier cave it got high-centred on a 7.8 cm boulder. The [[Cave world]] now has only LiDAR-level rocks (user's choice for testing) | depth camera, a tilted second LiDAR or bumpers |
| 15 | Robot | The effective track width (0.43 m) was measured in simulation only ([[Gazebo simulation]]) | measure turn rate against command on the real robot |
| 19 | Robot | Motor stall torque is assumed (0.8 kg·cm). With the rated 0.35 kg·cm the simulated robot can't pivot at all ([[Robot model]]) | datasheet stall torque; test a pivot on rock with the real robot |
| 20 | Robot | Leading with the bogie climbed worse than leading with the rocker in simulation ([[Rock climbing]]) | compare both on the real robot |
| 16 | Robot | The ESP32 firmware and the Pi nodes ([[explorer_bringup]]) are tested only without hardware: firmware compiled, nodes against a simulated ESP32 and X2. `TICKS_PER_REV`, the PI gains, the IMU mounting in the URDF and the X2's `angle_offset_deg` are not measured yet | bench test steps in [[explorer_bringup]] |
| 17 | Robot | LM393 slot encoders are single-channel, so direction comes from the command. If a wheel is pushed backwards against the command, odometry counts it the wrong way. 20 slots give only 10 mm resolution | quadrature encoders |
| 18 | Model | IMU height is assumed, and its +y axis (forward) is derived from +x left, +z down ([[Robot model]]) | check: rotating the robot left must give a negative gyro z on the chip (z points down) |
| 21 | Receiver | The receiver Pi has no RTC, so every boot starts at 2026-06-05, and its only time source is the explorer (192.168.123.1) over `bat0`. The mesh is brought up by hand with `~/demo_com/start-mesh.sh`, not at boot. Two causes, both fixed on 2026-10-14: (a) `chrony.service` was disabled; (b) the script's `nmcli device set wlan0 managed no` fires NetworkManager's `20-chrony-onoffline` hook while `bat0` has no address, which marks the source **offline**. NM doesn't manage `bat0`, so nothing marks it online again and chrony never syncs until it is restarted. Until it syncs, latency = receive − `transmission_stamp` is meaningless ([[Message envelope]]), and `colcon build` skips copying edited Python files because the old installed copies look newer | `start-mesh.sh` step 8 now runs `chronyc online`, `burst`, `makestep` and `waitsync`, and prints whether the clock synced. Manual fallback: `sudo chronyc online && sudo chronyc burst 4/4 && sleep 10 && sudo chronyc makestep`. If the clock was wrong during a build, `rm -rf build/mesh_nodes install/mesh_nodes` and rebuild. Not fixed: the mesh still isn't started at boot |
| 22 | Receiver | Two senders on one ROS domain make `tf_rolling_metrics` reset its state on almost every message (the session ID flips back and forth), so it never reports ([[Receiver (external)]]) | one sender per domain, or track state per session |
| 23 | Receiver | TF throughput counts 56 bytes per transform (the 7 doubles), not the real serialised size. The throughput score's 7.31 KB/s reference uses the same estimate | measure serialised size if absolute KB/s matters |
| 24 | Receiver | A total outage reads as NaN, not 0 %. With no heartbeat in the window, `expected` = 0 and PDR is written as null; `hop_count`/`tq` are null when `batctl tr` finds no route (checked in an older receiver copy, `~/.local/share/Trash/files/pi_mesh_nodes/`; the Pi's current version not checked). Seen in all 3 [[Relay field tests 2026-10-17]] | count null windows as 0 % in the report, or log the heartbeat age |
| 26 | Navigation | In passages narrower than about 0.9 m, the reverse-capable MPPI controller can stand still (speed under 0.03 m/s) with a valid path out behind the robot, and BackUp fails with "Collision Ahead". Seen in reverse-out run 1 and all 3 tunnel-reverse runs ([[Tunnel-reverse 2026-10-20]]) | Worked around in `tunnel_reverse.launch.py`: the planner plans for a 0.22 m round robot, and the coordinator backs out 1 m along its own track when stuck. Cause not fixed (MPPI cost tuning) |
| 27 | Navigation | With tunnel-reverse at full speed, exploring a short pocket or dead end is two U-turns (or a U-turn, backing out and Nav2's Spin recovery) within a minute at nearly the same place: ≥ 300° in 60 s with < 1 m net. One per run in all 3 runs of the second confirmation ([[Nav speed 2026-10-21]]) | Not a spin. The user changed the rotation-event definition to path driven < 1 m in 60 s (2026-10-21); the trips still happen and cost turning time |
| 28 | Tools | "Plans through unknown cells" was checked against the global costmap rosview last received (1 Hz); cells the map revealed in the last 1–2 s were flagged although known. Since 2026-10-21 (user's decision) a plan counts only if the cell is still unknown in the next costmap. One real case remains: 74 plans to a goal at the chamber-F entrance ended on a cell that stayed unknown ([[Nav speed 2026-10-21]]) | lead: NavFn keeps a goal on an unknown cell when its potential is valid; check the goal cell's cost and keep frontier goals off unknown costmap cells |
| 29 | Navigation | The rotation shim falls back to MPPI silently (DEBUG log) when its sampled path point fails to transform, or its 1 s rotation check hits a lethal cell. Forward MPPI then stands still with the path behind it until the 30 s give-up; seen once with 0.36 m to the nearest boulder ([[Nav speed 2026-10-21]]) | run with `log_level:=controller_server:=debug` until it happens again |
| 30 | Tools | `demo_recorder` records screen pixels (x11grab), not the windows themselves: a desktop notification, a window dragged on top or a moved Gazebo/RViz window ends up in the video (a VS Code "build successful" pop-up did in the 2026-10-24 test). It tiles the windows once, at start ([[Demo recording]]) | turn on GNOME Do Not Disturb and leave the windows alone while recording |
| 31 | Tools | The rover tools' coverage (`rosview.py`, `sim_loop.py`, experiments) treats the map frame as the world frame, so it is wrong for a run that does not start at (0, 0): a random start at (10.9, −1.4) read 5.2 % with more known area than floor. `demo_hud` moves the map by the start pose and is right ([[Demo recording]]) | pass the spawn pose to rosview as demo_hud does, before running experiments from other starts |
| 25 | Mesh | In open ground the route flips between direct and the Pi Zero 2 W repeater, because both routes' TQ stay close ([[Relay field tests 2026-10-17]]) | place the repeater where the direct link is clearly gone, lower `hop_penalty`, or try `BATMAN_V` |
